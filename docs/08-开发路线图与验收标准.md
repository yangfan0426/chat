# 08 · 开发路线图与验收标准

## 1. 里程碑规划

```
M0 插件内核 ──▶ M1 底座聊天(单Provider插件) ──▶ M2 多Provider插件 ──▶ M3 多模态 ──▶ M4 knowledge-base插件
 (1 周)            (1.5 周)                       (1 周)               (0.5~1 周)       (2 周)
```

每个里程碑结束产出**可运行、可验收**的版本。M0 是插件架构的地基，必须先立住：内核契约 + SDK + 一个示例插件，全部后续开发都建立在这套契约上。

## 2. M0 — 插件内核与契约

**任务拆解**

| # | 任务 | 产出 |
|---|---|---|
| 0.1 | monorepo 初始化（pnpm workspace、ESLint/Prettier/husky） | 可提交的工程骨架 |
| 0.2 | `packages/kernel`：Service/Event 接口定义、manifest 类型、契约版本 | 契约包 |
| 0.3 | 集成 Cordis：`apps/server` 启动入口、插件组合配置（`config/plugins.ts`）、依赖图加载、失败回滚 | 可运行的空底座 |
| 0.4 | `packages/plugin-sdk`：apply ctx（注册服务/路由/事件/配置项）、dispose 统一清理 | 插件开发 SDK |
| 0.5 | `config` + `http` + `events` 三个内核服务落地；zod 环境变量校验；pino 日志 | 内核公共服务 |
| 0.6 | `plugin-hello` 示例插件：声明 config、注册路由与事件、验证加载/卸载/回滚 | 插件模板与联调样例 |
| 0.7 | `/healthz` + `/api/plugins`（已加载插件清单） | 可观测性 |

**验收标准**
- [ ] 示例插件通过组合配置启停：启用后路由可访问，停用后路由消失且无残留订阅
- [ ] 插件 A `using` 插件 B 的服务：B 未启用时 A 按策略跳过加载，日志给出明确原因
- [ ] 加载中途失败：已加载插件全部 dispose，进程退出码非 0

## 3. M1 — 底座聊天链路（core-chat + 单 Provider 插件）

| # | 任务 |
|---|---|
| 1.1 | docker compose 起 PostgreSQL + pgvector；`core-storage-pg` 插件（database 服务、迁移执行） |
| 1.2 | `core-chat` 插件：会话/消息表、会话 CRUD 路由、历史分页 |
| 1.3 | `plugin-openai`（OpenAI 兼容协议）：config 声明（apiKey/baseUrl/models）、实现 `llm:provider/openai-compatible` 服务 |
| 1.4 | `llm` 内核服务：模型路由表、`stream()` 分发、能力校验（上下文裁剪、vision 422） |
| 1.5 | 聊天管线：`chat/request` 事件 → generate → 落库 → `chat/message-completed` |
| 1.6 | `POST /api/chat` SSE（message-start/delta/end 事件）+ 中断（AbortSignal 全链路传播） |
| 1.7 | 前端：聊天页（fetch+ReadableStream 读 SSE，EventSource 不支持 POST）、Zustand 流式缓冲、会话侧边栏、Markdown/代码高亮渲染 |

**验收标准**
- [ ] docker compose up 后配置一个模型即可在页面流式对话
- [ ] 刷新页面后会话与历史完整恢复
- [ ] 中断生成后历史里的 assistant 消息包含已生成内容且标记 `aborted`
- [ ] 后端日志记录插件名、模型与 token 用量

## 4. M2 — 多 Provider 插件

| # | 任务 |
|---|---|
| 2.1 | `plugin-deepseek` / `plugin-anthropic` 插件（复用共享的 OpenAI 兼容实现包） |
| 2.2 | `models` 聚合服务：跨插件模型清单汇总、能力标注下发 |
| 2.3 | 前端模型选择器（按服务商分组，标注 vision/上下文能力） |
| 2.4 | 设置页：插件配置表单由 manifest `config` 声明自动渲染（secret 脱敏） |
| 2.5 | 上下文超限自动重试策略；`plugin/settings-changed` 事件驱动客户端重建 |

**验收标准**
- [ ] 同一页面可在 ≥3 家服务商模型间切换对话
- [ ] API Key 不出现在任何前端响应/网络面板中
- [ ] 修改插件配置无需重启服务即生效

## 5. M3 — 多模态（图片理解）

| # | 任务 |
|---|---|
| 3.1 | `storage` 内核服务（本地驱动）+ `POST /api/files` / `GET /api/files/:id` |
| 3.2 | 消息 attachments 链路：前端预览/删除已选图片 → 随消息提交 |

**验收标准**
- [ ] 选 vision 模型可上传截图提问并得到正确回答；选纯文本模型时图片入口禁用并提示
- [ ] 刷新后图片消息完整回显

## 6. M4 — knowledge-base 插件（RAG）

| # | 任务 |
|---|---|
| 4.1 | 插件骨架：manifest、`kb_*` 表与迁移、文档上传/列表/删除路由 |
| 4.2 | Ingest worker（插件内进程内队列：解析→分块→embed→入库，状态机+重试+启动恢复） |
| 4.3 | 解析与分块模块（unpdf / mammoth；结构感知分块；含单元测试） |
| 4.4 | `POST /api/kb/search` 检索调试接口 |
| 4.5 | 挂接聊天管线：订阅 `chat/request` → 检索 → systemPrompt 注入 → citations 随 message-end 下发 |
| 4.6 | 前端：知识库管理页（上传/状态/删除/分块预览）、会话关联知识库开关、回答引用卡片 |

**验收标准**
- [ ] 上传 3 份 ≥50 页的 PDF，状态机全部到达 ready
- [ ] 针对文档内容提问，回答正确且带来源标注；文档外"胡问"明确说明知识库未覆盖
- [ ] 停用 knowledge-base 插件后，聊天功能完全不受影响（验证插件隔离性）
- [ ] 检索调试接口返回 Top-K 块及分数

## 7. 风险登记

| 风险 | 等级 | 应对 |
|---|---|---|
| SSE 被反向代理/浏览器缓冲，流式卡顿 | 高 | 响应头加 `X-Accel-Buffering: no`；dev 环境直连后端端口调试；文档记录 nginx 配置 |
| Cordis v4 API 变动或文档不足 | 中 | 锁定版本；内核封装隔离，升级只改封装层 |
| 插件架构过度设计导致进度拖延 | 中 | M0 严格限定内核只做四件事；契约先简后繁，**不为想象中的需求设计扩展点** |
| 各家 API 行为差异（图片格式、错误码） | 中 | provider 插件内集中处理；每接一家先在调试脚本中验证消息格式 |
| RAG 召回质量不达预期 | 中 | 检索调试接口 + 分块可视化提前做，先调参再谈混合检索 |
| Windows 开发环境依赖编译问题 | 低 | 解析库全选纯 TS 实现；docker 兜底 |

## 8. 工程规范（全程执行）

- 提交前 lint-staged 跑 ESLint + Prettier；commit message 用约定式提交（feat/fix/chore/docs）
- 核心纯逻辑（分块、prompt 组装、上下文裁剪、错误映射、插件加载/回滚）必须有 Vitest 单测
- 每个插件自带 README：manifest 示例、配置说明、提供的服务与订阅的事件
- 每个里程碑结束更新 README「快速开始」与本文档勾选验收项
