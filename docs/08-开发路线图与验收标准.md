# 08 · 开发路线图与验收标准

## 1. 里程碑规划

```
M1 骨架+单模型对话 ──▶ M2 多模型聚合+持久化 ──▶ M3 多模态 ──▶ M4 RAG 知识库
  (1.5~2 周)              (1 周)                (0.5~1 周)        (2 周)
```

每个里程碑结束产出**可运行、可验收**的版本；M1 优先打通"一条最短链路"（前端发消息 → 后端调一个模型 → 流式回到页面）。

## 2. M1 — 项目骨架与单模型流式对话

**任务拆解**

| # | 任务 | 产出 |
|---|---|---|
| 1.1 | monorepo 初始化（pnpm workspace、ESLint/Prettier/husky、`packages/shared`） | 可提交的工程骨架 |
| 1.2 | docker compose 起 PostgreSQL + pgvector；Drizzle schema 初始化（conversations/messages） | 数据库可连，迁移可跑 |
| 1.3 | Fastify 启动框架：环境变量 zod 校验、CORS、错误统一格式、健康检查 | 后端骨架 |
| 1.4 | Provider 适配层雏形：`openai-compatible` 协议 + `stream()` 接口；环境变量注入一个模型 | 可调通一家模型 |
| 1.5 | `POST /api/chat` SSE + `GET /api/conversations(-/:id/messages)` + 会话 CRUD | 核心 API |
| 1.6 | 前端：聊天页（消息列表、输入框）、Zustand 流式缓冲、`fetch` SSE 客户端（EventSource 不支持 POST，用 fetch + ReadableStream） | 页面可见流式输出 |
| 1.7 | 前端：会话侧边栏 CRUD；Markdown + 代码高亮渲染；中断按钮（AbortController） | 基础可用体验 |

**验收标准**
- [ ] docker compose up 后，配置一个模型即可在页面流式对话
- [ ] 刷新页面后会话与历史完整恢复
- [ ] 中断生成后历史里的 assistant 消息包含已生成内容且标记 `aborted`
- [ ] 后端日志记录每次请求的模型与 token 用量

## 3. M2 — 多模型聚合与会话持久化完善

| # | 任务 |
|---|---|
| 2.1 | providers/models 表 + 增删改查 API（key 加密存储、脱敏返回） |
| 2.2 | 适配层扩展：anthropic / google 协议；provider 工厂 + 内存缓存 |
| 2.3 | 前端模型选择器（按服务商分组，标注 vision/上下文能力） |
| 2.4 | 能力校验（非 vision 模型传图 → 422；上下文裁剪策略落地） |
| 2.5 | 设置页：服务商配置 UI |
| 2.6 | token 用量落库（messages.usage） |

**验收标准**
- [ ] 同一页面可在 ≥3 家服务商模型间切换对话
- [ ] API Key 不出现在任何前端响应/网络面板中
- [ ] 超长历史会话自动裁剪，无上下文超限报错（触发 400 时按设计自动重试一次）

## 4. M3 — 多模态（图片理解）

| # | 任务 |
|---|---|
| 3.1 | `POST /api/files` 上传 + `GET /api/files/:id` 读取 |
| 3.2 | 消息 attachments 链路：前端预览/删除已选图片 → 随消息提交 |
| 3.3 | 适配层多模态消息映射（OpenAI image_url / Anthropic base64 / Google inlineData） |
| 3.4 | 历史消息中图片正确回显 |

**验收标准**
- [ ] 选 vision 模型可上传截图提问并得到正确回答；选纯文本模型时图片入口禁用并提示
- [ ] 刷新后图片消息完整回显

## 5. M4 — RAG 知识库

| # | 任务 |
|---|---|
| 4.1 | knowledge_bases / documents / chunks 表 + HNSW 索引迁移 |
| 4.2 | 文档上传 API + Ingest worker（进程内队列：解析→分块→embed→入库，状态机+重试+启动恢复） |
| 4.3 | 解析库接入（unpdf / mammoth）与清洗、分块模块（含单元测试） |
| 4.4 | `POST /api/kb/search` 调试接口 |
| 4.5 | 聊天链路接入：会话关联 kb → 检索 → system prompt 注入 → citations 返回 |
| 4.6 | 前端：知识库管理页（上传/列表/状态/删除/分块预览）、会话关联知识库开关、回答引用卡片展示 |

**验收标准**
- [ ] 上传 3 份 ≥50 页的 PDF，状态机全部到达 ready
- [ ] 针对文档内容提问，回答正确且带来源标注；对文档外的"胡问"，模型明确说明知识库未覆盖
- [ ] 检索调试接口返回 Top-K 块及分数
- [ ] 删除文档后其 chunks 与向量同步清除，后续检索不再命中

## 6. 风险登记

| 风险 | 等级 | 应对 |
|---|---|---|
| SSE 被反向代理/浏览器缓冲，流式卡顿 | 高 | 响应头加 `X-Accel-Buffering: no`；dev 环境直连后端端口调试；文档记录 nginx 配置 |
| 各家 API 行为差异（tool 字段、图片格式） | 中 | 适配层集中处理；每接一家先在调试脚本中验证消息格式 |
| RAG 召回质量不达预期 | 中 | 调试接口 + 分块可视化提前做（4.4/4.6），先调参再谈混合检索 |
| `ai` SDK 版本 API 变动 | 中 | 锁定版本；适配层隔离 |
| Windows 开发环境依赖编译问题 | 低 | 解析库全选纯 TS 实现；docker 兜底 |
| 上传恶意/超大文件 | 低 | 类型白名单 + 20MB 上限 + 后端二次校验 |

## 7. 工程规范（全程执行）

- 提交前 lint-staged 跑 ESLint + Prettier；commit message 用约定式提交（feat/fix/chore/docs）
- 核心纯逻辑（分块、prompt 组装、上下文裁剪、错误映射）必须有 Vitest 单测
- 每个里程碑结束更新 README「快速开始」与本文档勾选验收项
