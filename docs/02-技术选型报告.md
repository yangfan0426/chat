# 02 · 技术选型报告

> 结论速览：**React 18 + Vite + TS / Tailwind + shadcn/ui ｜ Fastify + Cordis 插件内核 + Vercel AI SDK ｜ PostgreSQL + pgvector ｜ Drizzle ｜ 本地文件存储**

## 0. 架构范式

本项目采用**底座 + 插件**架构，范式参考 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（"一切皆插件"，内核为 Cordis）。选型围绕这一范式展开：凡是可以被替换的组件（模型、存储、RAG），一律以插件形态接入，底座不持有具体实现。

## 1. 前端框架与构建

### 候选：Next.js vs React SPA（Vite）

| 维度 | Next.js（SSR/全栈） | React SPA + Vite（前后端分离） |
|---|---|---|
| 架构契合 | 前后端一体，违背"前后端分离"诉求 | ✅ 完全契合 |
| SSE 流式 | 需 Route Handler，部署形态受限 | ✅ 直连后端，灵活 |
| 构建速度 | 中等 | ✅ 极快（HMR <100ms） |
| 学习/调试成本 | 高（RSC、缓存规则复杂） | ✅ 低 |

**决策：React 18 SPA + Vite。** 本项目无 SEO 需求（自用工具），前后端分离是硬性诉求，SPA 方案心智负担最小。后端独立部署后，前端也可随时迁移到 Next.js 或打包成 Tauri 桌面应用。

### UI 方案：Tailwind CSS + shadcn/ui

- Tailwind：样式就近维护，聊天类密集 UI 开发效率远高于传统 CSS-in-JS。
- shadcn/ui：组件源码直接落入项目（非 npm 黑盒），对话框/下拉/滚动区等聊天所需组件开箱即用，且易于深度定制。
- Markdown 渲染：`react-markdown` + `remark-gfm` + `rehype-highlight`（代码高亮）。
- 状态管理：Zustand（会话状态、流式消息缓冲）；服务端状态用 TanStack Query。

## 2. 插件内核：Cordis

### 候选：Cordis vs 自研 DI 内核 vs 重型框架（NestJS/WireJS）

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| Cordis | ✅ 成熟插件生命周期管理（来自 Koishi 生态，dsh 同款内核）；时空可组合：插件即依赖注入单元，卸载副作用可完整回滚；npm 直接依赖 | 文档以英文/社区为主；v4 API 较新 | ✅ **选定** |
| 自研插件内核 | 完全可控 | 重复造轮子：生命周期、依赖图、热卸载、事件总线都要自己写，且最难的部分（回滚正确性）恰恰最容易出错 | 弃 |
| NestJS | 企业级 DI | 是应用框架而非插件内核，无法承载"第三方插件热插拔" | 弃 |

**决策：直接依赖 npm 上的 `cordis`，不 vendor 源码。** dsh 选择 vendor 是因为它要把内核钉死在某个版本防止漂移；我们是新应用，跟随 semver 升级即可。Cordis 只做一件事——插件的加载/卸载与依赖关系管理——正好对应"底座保持小、变化通过协议接入"的架构目标。

**运行时约束**：Cordis 与 dsh 生态要求 Node.js `^22.19.0 || >=24.0.0`，工程化与 docker 镜像需按此基线。

## 3. 后端框架

### 候选：Fastify vs Express vs NestJS vs Hono

| 框架 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| Fastify | ✅ 性能最好（JSON 序列化快）、Schema 校验内建、TS 类型推导好 | 插件生态略小于 Express | ✅ **选定** |
| Express | 生态最大、资料最多 | 性能平庸、TS 支持差、多年停滞 | 弃 |
| NestJS | 企业级架构（DI/装饰器） | 重量级；DI 已由 Cordis 承担，重复 | 弃 |
| Hono | 极轻、边缘运行时友好 | 生态年轻，Node 服务器场景无优势 | 弃 |

**决策：Fastify。** 自带 `fast-json-stringify` 与 schema 校验，SSE 场景性能与 Express 相当但序列化更优；`@fastify/cors`、`@fastify/multipart`、`@fastify/static` 覆盖全部需求。**注意**：Fastify 在此仅作为 HTTP 适配层存在，业务组件全部是 Cordis 插件，HTTP 路由只是插件暴露能力的一种方式。

### AI 调用层：Vercel AI SDK

- `@ai-sdk/openai`、`@ai-sdk/anthropic`、`@ai-sdk/google` 等按厂商分包，统一 `streamText()` API。
- 原生支持 SSE 流式、tool calling、结构化输出、图像输入；Provider 兼容层（OpenAI-compatible）可接入 Kimi/DeepSeek 等任意兼容 OpenAI 协议的国产模型。
- 放弃自研适配层直接裸用各厂商 SDK 的原因：流式协议、错误处理、abort 语义已被抽象统一，省去大量胶水代码。

## 4. 数据库与向量检索

### 候选矩阵

| 方案 | 关系数据 | 向量检索 | 运维成本 | 结论 |
|---|---|---|---|---|
| PostgreSQL + pgvector | ✅ 原生 | ✅ 余弦/内积/IP，HNSW 索引 | ✅ 单容器 | ✅ **选定** |
| SQLite + 向量扩展 | ✅ | ⚠️ 需额外扩展，Windows 编译麻烦 | ✅ 最低 | 备选（单机极致轻量时） |
| Milvus / Qdrant | ❌ 需额外库 | ✅ 性能强 | ❌ 独立服务，过重 | 数据量到百万 chunks 前不需要 |
| Pinecone 等云服务 | ❌ | ✅ | ⚠️ 数据出域、有费用 | 弃 |

**决策：PostgreSQL 16 + pgvector。** 会话/消息/配置/向量一个库搞定，事务一致性天然保证（删文档可同时清理 chunks）；万级 chunks 下 HNSW 检索毫秒级，个人/小团队绰绰有余。避免引入第二个有状态服务是最主要的架构收益。

## 5. ORM：Drizzle vs Prisma

| 维度 | Drizzle | Prisma |
|---|---|---|
| 类型安全 | ✅ SQL 风格，类型推导到列 | ✅ 生成客户端 |
| 轻量/可控性 | ✅ 纯 TS，无引擎二进制 | ❌ Rust 引擎，体积大 |
| 迁移 | `drizzle-kit` 生成 SQL | `prisma migrate` |
| 生态成熟度 | 成长中 | 更成熟 |

**决策：Drizzle。** 与 pgvector 的自定义向量类型结合更自然（可用 `sql` 片段直写 `<=>` 操作符），且无需引入 Prisma 引擎这一额外复杂度。

## 6. 文件与对象存储

- **阶段一：本地磁盘**（`data/uploads/`），数据库记录路径。简单、零依赖、备份即拷贝目录。
- 抽象 `StorageDriver` 接口（`put/get/delete`），预留 S3/MinIO 实现。
- 上传限制：单文件 ≤ 20MB；类型白名单（pdf/docx/txt/md/png/jpg/webp）。

## 7. 文档解析库

| 格式 | 库 | 说明 |
|---|---|---|
| PDF | `unpdf`（纯 TS，无 native 依赖） | 文本型 PDF；扫描件不处理 |
| Word | `mammoth` | docx → 纯文本，保留段落结构 |
| TXT / MD | Node 原生 | — |
| 后续扩展 | `tesseract.js` | OCR（范围外） |

## 8. RAG 编排

- 不引入完整 LangChain.js：本项目 RAG 链路（分块 → embed → 检索 → 拼 prompt）非常固定，用 `ai` SDK 的 `embed()` / `embedMany()` + 手写检索即可，避免框架黑盒与版本折腾。
- Embedding 模型走 OpenAI 兼容接口（`text-embedding-3-small` 或国产等价模型），通过 provider 配置统一接入。

## 9. 工程化配套

| 项目 | 选型 | 备注 |
|---|---|---|
| 包管理 | pnpm + workspace | monorepo：`apps/web`、`apps/server`、`packages/shared`、`plugins/*` |
| 插件内核 | cordis | 插件生命周期与依赖注入（详见 §2） |
| 共享类型 | `packages/shared` | DTO/枚举前后端共享 |
| Lint/格式 | ESLint + Prettier + husky/lint-staged | 提交前强制 |
| 环境变量 | `.env` + zod 校验启动 | 缺关键配置直接拒绝启动 |
| 部署 | docker compose | app + postgres 两个服务 |
| 日志 | pino（Fastify 默认） | JSON 日志 |
| 测试 | Vitest（单元）+ 少量集成测试 | 以核心逻辑（分块、prompt 组装、检索）为主 |

## 10. 选型风险与回退方案

| 风险 | 应对 |
|---|---|
| `ai` SDK 大版本 API 变更 | 适配层集中封装，升级只改一处 |
| pgvector 性能不满足（chunks 达百万级） | 迁移向量至专用库，关系数据不动；HNSW 索引先撑住 |
| Windows 上某些依赖编译失败（如 sharp） | 解析库均选纯 TS 实现；CI 用 Linux 容器兜底 |
| Drizzle 生态缺陷 | 复杂查询可降级为手写 SQL（Drizzle 原生支持），无需换 ORM |
