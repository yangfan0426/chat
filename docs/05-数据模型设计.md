# 05 · 数据模型设计

> 数据库：PostgreSQL 16 + pgvector。ORM：Drizzle。所有表带 `id uuid pk default gen_random_uuid()`、`created_at timestamptz default now()`（下表省略公共字段）。

## 1. ER 关系总览

```
providers 1───n models
conversations 1───n messages
knowledge_bases 1───n documents 1───n chunks
conversations n───n knowledge_bases   （会话关联知识库）
```

## 2. 表结构

### 2.1 providers（服务商）

| 列 | 类型 | 说明 |
|---|---|---|
| name | text unique | 标识：deepseek / openai / kimi |
| label | text | 展示名 |
| base_url | text | API 地址 |
| api_key_encrypted | text | 加密存储（AES-256-GCM，密钥来自环境变量） |
| embedding_model | text null | embedding 模型 id |
| embedding_dimension | int null | 向量维度，如 1536/1024 |

### 2.2 models（模型）

| 列 | 类型 | 说明 |
|---|---|---|
| provider_id | uuid fk → providers | |
| model_id | text | 厂商侧模型名（如 deepseek-chat） |
| label | text | 展示名 |
| context_window | int | 上下文窗口 token 数 |
| supports_vision | bool | 是否多模态 |
| is_default | bool | 默认选中 |

唯一约束：`(provider_id, model_id)`。

### 2.3 conversations（会话）

| 列 | 类型 | 说明 |
|---|---|---|
| title | text | 标题（默认取首条消息前 20 字） |
| model_id | text null | 当前选用模型（冗余 models.model_id，便于快照与切换） |
| pinned | bool default false | 置顶 |

### 2.4 knowledge_bases（知识库）

| 列 | 类型 | 说明 |
|---|---|---|
| name | text | |
| embedding_provider_id | uuid fk → providers | 向量用哪个服务商的 embedding 模型 |
| is_default | bool | 上传未指定库时落入此库 |

### 2.5 conversation_kbs（会话 ↔ 知识库关联）

| 列 | 类型 |
|---|---|
| conversation_id | uuid fk → conversations on delete cascade |
| kb_id | uuid fk → knowledge_bases on delete cascade |

联合主键 `(conversation_id, kb_id)`。

### 2.6 messages（消息）

| 列 | 类型 | 说明 |
|---|---|---|
| conversation_id | uuid fk → conversations on delete cascade | |
| role | text | `system` / `user` / `assistant` |
| content | text | Markdown 正文 |
| attachments | jsonb null | `[{type, fileId, name}]` |
| model_id | text null | assistant 消息记录生成所用模型 |
| finish_reason | text null | `stop` / `aborted` / `error` |
| prompt_tokens | int null | |
| completion_tokens | int null | |

**索引**：`(conversation_id, created_at desc)` —— 历史分页查询。

> `system` 消息不落库：RAG 注入的 system prompt 为每次请求动态组装，仅落库用户与助手消息。

### 2.7 documents（知识库文档）

| 列 | 类型 | 说明 |
|---|---|---|
| kb_id | uuid fk → knowledge_bases on delete cascade | |
| filename | text | 原始文件名 |
| mime_type | text | |
| size_bytes | int | |
| storage_path | text | StorageDriver 内部路径 |
| status | text | **状态机，见 §3** |
| error | text null | 失败原因（展示用） |
| chunk_count | int default 0 | |

**索引**：`(kb_id, status)` —— worker 拉取待处理任务。

### 2.8 chunks（文本分块 + 向量）

| 列 | 类型 | 说明 |
|---|---|---|
| document_id | uuid fk → documents on delete cascade | |
| kb_id | uuid fk | 冗余，检索时过滤用 |
| chunk_index | int | 文档内序号 |
| content | text | 分块正文 |
| embedding | vector(1536) | 维度按实际 embedding 模型定 |
| token_count | int | |

**索引**：
- `(document_id, chunk_index)`
- **HNSW**：`create index on chunks using hnsw (embedding vector_cosine_ops);`
- `(kb_id)` —— 检索过滤。

## 3. documents 状态机

```
            ┌──────────┐  领取任务   ┌───────────┐
  上传 ────▶│ pending  │───────────▶│ parsing   │
            └──────────┘            └─────┬─────┘
                              解析+分块成功 │  解析失败
                                    ┌─────▼─────┐  向量化成功   ┌────────┐
                                    │ embedding │────────────▶│ ready  │
                                    └─────┬─────┘             └────────┘
                                          │ 失败
                                    ┌─────▼─────┐ ◀── retry ──┐
                                    │  failed   │             │
                                    └───────────┘             │
                                          ▲───────────────────┘
                                    （任何阶段异常均落入 failed）
```

- 所有转移由 ingest worker 在数据库事务内完成；进程重启后 `parsing`/`embedding` 状态的文档在启动扫描时重置回 `pending` 重新执行（幂等：chunks 先删后插）。
- `ready` 为终态（删除文档除外）。

## 4. 容量与增长预估

| 表 | 预估 | 说明 |
|---|---|---|
| messages | 万级/年 | 自用场景，单库无压力 |
| chunks | 万~十万级 | 每文档 20~200 chunks；HNSW 在此量级检索 <50ms |
| 向量存储 | 1536 维 float32 ≈ 6KB/条 | 10 万条 ≈ 600MB，可接受 |

达到百万 chunks 量级时的演进路径：向量迁移 Qdrant/Milvus，关系表结构不变（见技术选型报告 §9）。

## 5. 数据清理策略

- 删除会话/文档均为物理删除（自用场景，不做软删），级联已建。
- 文件存储中的孤儿文件：每日轻量清理任务比对 storage 与 documents 表（阶段二加入）。
