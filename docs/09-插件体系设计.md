# 09 · 插件体系设计

> 本项目的"底座 + 插件"架构参考 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的设计哲学：**一切皆插件，没有特权核心**。插件内核使用 Cordis（依赖注入 + 生命周期管理），插件间通过 Service 与 Event 协作。本文定义插件的契约规范，是编写任何插件前必读文档。

## 1. 插件是什么

一个插件是一个符合契约的 npm 包/本地包，包含：

- **Manifest**：元信息与声明（名称、版本、依赖的服务、提供的配置项、能力）
- **Apply 函数**：插件入口，内核调用它完成注册；返回 dispose 函数用于卸载回滚
- **可选的 UI 扩展**：前端侧注册的设置卡片、消息操作等（阶段二）

```
插件 = manifest（声明） + apply(ctx)（注册） + dispose()（回滚）
```

## 2. Manifest 规范

```ts
interface PluginManifest {
  name: string                  // 唯一标识，如 'plugin-deepseek'（带 npm scope 前缀亦可）
  version: string               // semver
  description?: string
  using?: ServiceRef[]          // 依赖的内核/其他插件服务（缺失则拒绝加载）
  provides?: ServiceRef[]       // 对外提供的服务名
  config?: ConfigField[]        // 声明式配置项（底座渲染设置表单）
  events?: { publish: string[]; subscribe: string[] }  // 事件契约（文档性约束）
  ui?: UiContribution[]         // UI 扩展点贡献（阶段二）
}
```

### 配置项声明（配置中心据此渲染表单）

```ts
interface ConfigField {
  key: string
  type: 'string' | 'secret' | 'number' | 'boolean' | 'select'
  label: string
  required?: boolean
  secret?: boolean              // 加密落库（API Key 等），接口脱敏返回
  options?: { value: string; label: string }[]   // type=select
  default?: unknown
}
```

**示例**：deepseek provider 插件的 manifest 片段：

```ts
{
  name: 'plugin-deepseek',
  version: '0.1.0',
  using: ['config', 'http', 'llm'],
  provides: ['llm:provider/deepseek'],
  config: [
    { key: 'apiKey', type: 'secret', label: 'API Key', required: true },
    { key: 'baseUrl', type: 'string', label: 'Base URL', default: 'https://api.deepseek.com/v1' },
    { key: 'models', type: 'string', label: '模型清单(JSON)', required: true }
  ]
}
```

## 3. 生命周期

```
disabled ──启用──▶ applying ──成功──▶ active ──停用──▶ disposing ──▶ disabled
                      │失败               │            │失败→记录错误
                      ▼                  ▼            ▼
                 rolled back          服务可         回滚：
                 （无副作用残留）       被注入        注销路由/事件订阅/服务，
                                               释放定时器与进行中的任务
```

- **apply 必须幂等且可回滚**：注册的所有东西（路由、事件订阅、定时器、服务）都要登记到 ctx，dispose 时由内核统一清理。
- **加载顺序**：内核按 `using` 依赖图拓扑排序；循环依赖直接报错拒绝启动。
- **依赖服务不可用**：插件声明了 `using: ['database']` 而 storage 插件未启用 → 该插件跳过加载并记录警告（fail-fast 与否由组合配置决定）。

## 4. Service 契约（内核标准服务）

| 服务名 | 接口 | 说明 |
|---|---|---|
| `config` | `get<T>(plugin, key)` / `set(plugin, key, value)` | 插件配置读写；secret 类型自动加解密 |
| `http` | `registerRoute(method, path, handler)` / `registerSse(path, handler)` | 注册 REST/SSE 路由，自动挂 `/api` 前缀与错误包装 |
| `events` | `emit(event, payload)` / `on(event, handler)` | 类型化事件总线，dispose 自动退订 |
| `storage` | `put/get/delete` | 文件存储（本地驱动，接口预留 S3） |
| `database` | Drizzle 实例 | 由 core-storage-pg 提供 |
| `chat.pipeline` | `intercept(stage, handler)` | 挂接聊天管线（见 §5） |
| `models` | `list()` / `get(modelId)` | 聚合所有 provider 插件声明的模型与能力 |
| `llm` | `stream(req, handlers, signal)` / `embed(texts)` | 按模型分发到 provider 插件的实现 |

### 服务命名约定

- 内核服务：无前缀（`config`、`http`）
- 插件提供的服务：`llm:provider/<name>`、`storage:driver/<name>` 形式命名空间化，避免冲突

## 5. 管线（Pipeline）扩展

聊天请求处理采用阶段化管线，插件可拦截/改写：

```
request ─▶ [stage: assemble] 组装消息历史（core-chat）
        ─▶ [stage: enrich]   事件 chat/request：插件改写 systemPrompt / messages
        ─▶ [stage: generate] 调用 llm.stream 生成（不可拦截，只观察）
        ─▶ [stage: persist]  落库 + 事件 chat/message-completed
```

- **enrich 阶段**是知识库插件的挂接点：订阅 `chat/request`，检索命中则改写请求注入资料段，并把引用信息写入请求上下文，随 `message-end` 下发给前端。
- 管线处理器可异步、可按注册顺序链式执行；任一步抛错 → 管线中断，SSE 下发 `message-error`。

## 6. 插件类型与扩展点速查

| 想做什么 | 怎么做 |
|---|---|
| 接入一个新模型厂商 | 新 provider 插件：manifest 声明配置 + 实现 `llm:provider/x` 服务 |
| 给对话加能力（RAG/翻译/审查） | 插件订阅 `chat/request` 改写，或注册管线拦截器 |
| 存数据 | 注入 `database` 服务建表（迁移随插件走，见 §7） |
| 提供设置界面 | manifest `config` 声明 → 底座自动渲染表单（无需写 UI） |
| 自定义页面/按钮 | `ui` 贡献点（阶段二定义前端扩展契约） |
| 监听对话完成做统计 | 订阅 `chat/message-completed` |

## 7. 数据归属约定

- 每个插件在数据库中的表以插件名前缀命名空间（如 `kb_documents`、`kb_chunks`），迁移脚本随插件包提供，启动时由内核统一执行（记录已执行版本）。
- 插件被禁用/卸载时，**数据保留**（不级联删除），重新启用即可继续使用；彻底清理提供插件自带的清理命令。

## 8. 分发与版本

- 插件即 npm 包，manifest 中 `keywords` 含 `chat-plugin`（对标 dsh 的 `dsh-plugin` topic 约定）。
- 内核与插件间契约版本化：`packages/kernel` 导出契约版本，插件 manifest 声明 `compatibleWith: '^1.0'`，加载时校验不兼容则拒绝加载并给出明确提示。
- 内置插件（`core-*`、`plugin-*`）随仓库 monorepo 发布，版本与底座对齐；第三方插件独立发版。

## 9. 安全约束

- 插件代码运行在服务端同一进程（阶段一不做沙箱隔离），**只加载组合配置中显式启用的插件**——未启用即零代码执行。
- secret 类型配置仅经 `config` 服务在服务端内存中解密使用；任何 HTTP 响应不得包含密钥明文（脱敏规则由底座统一执行）。
- 插件注册的路由自动经过底座的认证/限流中间件（多用户阶段生效）。

## 10. 参考：与 dsh 设计对照

| dsh | 本项目 | 说明 |
|---|---|---|
| Cordis 内核 | Cordis（npm 依赖） | 同一插件内核 |
| 一切皆插件（模型/工具/会话/UI） | 一切皆插件（provider/存储/RAG/UI 预留） | 同范式，范围聚焦聊天 |
| `dsh-plugin` topic | `chat-plugin` keyword | 插件发现约定 |
| 配置层组合、无特权核心 | 组合配置 `config/plugins.ts` | `core-*` 也无特权 |
| 会话日志 append-only、resume/fork | 会话消息落库（阶段一先保证完整持久化） | resume/fork 列入路线图候选 |
