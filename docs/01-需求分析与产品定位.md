# 01 · 需求分析与产品定位

## 1. 产品定位

一个 **"底座 + 插件"架构的 AI 聊天平台**，架构范式参考 [DeepSeek Harness（dsh）](https://github.com/deepseek-ai/deepseek-harness) 的"一切皆插件"设计：

- **底座（Harness）**：只提供插件内核、会话管理、聊天主循环、事件总线等最小核心，自身**不内置任何具体模型或能力**；
- **插件（Plugin）**：模型接入、知识库 RAG、多模态、未来的一切增强，都以插件形式挂载到底座上，通过声明式配置组合，**替换能力 = 换插件，而不是改代码**。

> 与 dsh 的差异：dsh 是通用 Agent 执行底座（偏任务执行/编码场景）；本项目底座聚焦**聊天场景**（多会话、流式渲染、知识库问答），形态更轻。

### 与现成方案的关系

| 方案 | 形态 | 本项目相对优势 |
|---|---|---|
| ChatGPT / Kimi 官方应用 | 单一厂商产品 | 模型可插拔，数据本地持有 |
| ChatHub / LobeChat | 功能齐全的开源客户端 | 能力以插件接入，可自由重组、可二次开发 |
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | 一切皆插件的 Agent 底座 | 同为插件架构，但聚焦聊天场景，上手更轻 |
| Dify / FastGPT | 低代码 LLM 平台 | 面向开发者写插件扩展，而非面向运营编排 |

### 插件粒度

| 插件类型 | 示例 | 说明 |
|---|---|---|
| 模型 Provider 插件 | deepseek、openai、kimi… | 声明模型清单与能力，提供流式对话服务 |
| Embedding 服务 | 随 provider 插件提供 | RAG 插件通过依赖注入使用，不直接调厂商 API |
| 能力插件 | knowledge-base（RAG） | 注册设置页、检索服务，挂接聊天管线 |
| UI 扩展插件 | （预留） | 消息操作按钮、面板页签等扩展点 |

## 2. 目标用户与使用场景

- **首要用户**：开发者本人及小团队，自用 + 学习全栈 AI 应用开发链路。
- **典型场景**：
  1. 日常多模型对话（写作、翻译、代码问答）——多模型对比选最优回答；
  2. 上传技术文档 / 产品手册，基于文档做精确问答（RAG）；
  3. 截图或图片提问（多模态理解）。

## 3. 功能需求

### 3.1 需求优先级定义

- **P0**：没有它产品不可用
- **P1**：核心体验，首个可用版本应包含
- **P2**：重要增强，可延后

### 3.2 功能清单

| # | 功能 | 描述 | 优先级 | 归属 |
|---|---|---|---|---|
| F1 | 多会话管理 | 创建/重命名/删除/切换会话；侧边栏列表 | P0 | 底座 |
| F2 | 流式对话 | SSE 流式输出，Markdown + 代码高亮渲染 | P0 | 底座 |
| F3 | 中断生成 | 用户可主动中断流式输出 | P1 | 底座 |
| F4 | 多模型切换 | 按服务商分组选择模型，随时切换 | P0 | 底座 UI + Provider 插件 |
| F5 | 服务商配置 | 配置 baseURL / API Key / 模型清单，增删服务商 | P0 | Provider 插件（配置卡片由底座渲染） |
| F6 | 会话历史持久化 | 会话与消息落库，刷新后完整恢复 | P0 | 底座（存储插件） |
| F7 | 图片理解 | 上传图片，vision 模型多模态对话 | P1 | Provider 插件（能力声明） |
| F8 | 知识库文档管理 | 上传 PDF/Word/TXT/Markdown，解析状态可见，可删除 | P1 | knowledge-base 插件 |
| F9 | RAG 问答 | 会话可关联知识库，回答基于检索内容并支持引用来源 | P1 | knowledge-base 插件 |
| F10 | 检索调试 | 输入 query 查看召回的 chunks，辅助调优 | P2 | knowledge-base 插件 |
| F11 | token 用量统计 | 记录每次对话的输入/输出 token 数 | P2 | 底座 + Provider 插件上报 |
| F12 | 用户认证 | 多用户登录、会话隔离 | P2（首期单机自用，不做） | 底座（预留） |

### 3.3 明确不做（本期范围外）

- 语音输入/输出（TTS/ASR）
- Agent / Function Calling 工具调用
- 分享对话、公开发布
- 移动端原生 App（Web 响应式即可）
- 团队协作、权限体系

## 4. 非功能需求

| 类别 | 指标/要求 |
|---|---|
| 性能 | 首 token 延迟（TTFT）≤ 2s（不含模型本身延迟）；流式渲染 60fps 不卡顿；检索 Top-K 查询 ≤ 300ms（万级 chunks 内） |
| 并发 | 单用户场景为主，支撑 5 并发会话即可 |
| 数据 | API Key 仅存服务端，绝不下发前端；会话数据本地持有 |
| 可靠性 | 文档解析任务失败可重试；状态机可恢复，不产生悬挂的 pending 任务 |
| 可维护性 | 全栈 TypeScript，统一类型定义（前后端共享 DTO 类型） |
| 部署 | 单机 `docker compose` 一键起（app + postgres），无外部依赖 |

## 5. 关键约束与假设

1. **模型能力全部通过 Provider 插件提供**，底座不内置任何模型 SDK；embedding 服务同样由插件声明，知识库插件通过依赖注入获取。
2. 首个里程碑先实现**插件内核 + 一个 Provider 插件**跑通聊天链路，再扩展多模型与能力插件。
3. 文档解析首期只支持**文本型 PDF**；扫描件（需 OCR）列入后续。
4. 不考虑多租户，会话默认全局可见（单机）。
