# 01 · 需求分析与产品定位

## 1. 产品定位

一个**自建的多模型 AI 聊天平台**（对标 ChatHub / LobeChat 的自建版），核心差异是**内置 RAG 知识库问答能力**，让用户可以上传自有文档并基于文档提问。

### 与现成方案的关系

| 方案 | 说明 | 本项目相对优势 |
|---|---|---|
| 直接用 ChatGPT / Kimi 官方应用 | 单一厂商产品 | 可自由切换多家模型，对比效果；数据存在本地 |
| LobeChat / NextChat 等开源项目 | 功能齐全的自建方案 | 自建可深度定制 RAG 管道与检索调试，学习全链路 |
| 企业知识库产品（如 FastGPT） | 偏 B 端、重部署 | 轻量、单库部署、个人/小团队即可运行 |

## 2. 目标用户与使用场景

- **首要用户**：开发者本人及小团队，自用 + 学习全栈 AI 应用开发链路。
- **典型场景**：
  1. 日常多模型对话（写作、翻译、代码问答）——多模型对比选最优回答；
  2. 上传技术文档 / 产品手册，基于文档做精确问答（RAG）；
  3. 截图或图片提问（多模态理解）。

## 3. 功能需求

### 3.1 需求优先级定义

- **P0**：没有它产品不可用
- **P1**：核心体验，首个可用版本应包含
- **P2**：重要增强，可延后

### 3.2 功能清单

| # | 功能 | 描述 | 优先级 |
|---|---|---|---|
| F1 | 多会话管理 | 创建/重命名/删除/切换会话；侧边栏列表 | P0 |
| F2 | 流式对话 | SSE 流式输出，Markdown + 代码高亮渲染 | P0 |
| F3 | 中断生成 | 用户可主动中断流式输出 | P1 |
| F4 | 多模型切换 | 按服务商分组选择模型，随时切换 | P0 |
| F5 | 服务商配置 | 配置 baseURL / API Key / 模型清单，增删服务商 | P0 |
| F6 | 会话历史持久化 | 会话与消息落库，刷新后完整恢复 | P0 |
| F7 | 图片理解 | 上传图片，vision 模型多模态对话 | P1 |
| F8 | 知识库文档管理 | 上传 PDF/Word/TXT/Markdown，解析状态可见，可删除 | P1 |
| F9 | RAG 问答 | 会话可关联知识库，回答基于检索内容并支持引用来源 | P1 |
| F10 | 检索调试 | 输入 query 查看召回的 chunks，辅助调优 | P2 |
| F11 | token 用量统计 | 记录每次对话的输入/输出 token 数 | P2 |
| F12 | 用户认证 | 多用户登录、会话隔离 | P2（首期单机自用，不做） |

### 3.3 明确不做（本期范围外）

- 语音输入/输出（TTS/ASR）
- Agent / Function Calling 工具调用
- 分享对话、公开发布
- 移动端原生 App（Web 响应式即可）
- 团队协作、权限体系

## 4. 非功能需求

| 类别 | 指标/要求 |
|---|---|
| 性能 | 首 token 延迟（TTFT）≤ 2s（不含模型本身延迟）；流式渲染 60fps 不卡顿；检索 Top-K 查询 ≤ 300ms（万级 chunks 内） |
| 并发 | 单用户场景为主，支撑 5 并发会话即可 |
| 数据 | API Key 仅存服务端，绝不下发前端；会话数据本地持有 |
| 可靠性 | 文档解析任务失败可重试；状态机可恢复，不产生悬挂的 pending 任务 |
| 可维护性 | 全栈 TypeScript，统一类型定义（前后端共享 DTO 类型） |
| 部署 | 单机 `docker compose` 一键起（app + postgres），无外部依赖 |

## 5. 关键约束与假设

1. **模型能力通过服务商 API 提供**，不自建/微调模型；embedding 也调用 API（如 `text-embedding` 系列）。
2. 首个里程碑只接入 **1 家服务商、1 个文本模型**，跑通后再做多模型聚合。
3. 文档解析首期只支持**文本型 PDF**；扫描件（需 OCR）列入后续。
4. 不考虑多租户，会话默认全局可见（单机）。
