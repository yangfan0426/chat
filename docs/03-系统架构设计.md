# 03 · 系统架构设计

> 架构范式：**底座 + 插件**（参考 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的"一切皆插件"设计）。底座保持最小，一切可替换的组件都以插件形态接入。

## 1. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│                  前端 SPA（底座 UI + 插件 UI 扩展）                  │
│   会话列表 │ 聊天窗口(流式渲染) │ 模型选择器 │ 插件设置页/面板          │
└──────────────────────────┬───────────────────────────────────────┘
                           │ HTTP / SSE
┌──────────────────────────▼───────────────────────────────────────┐
│                        Fastify（HTTP 适配层）                       │
│        路由仅是插件能力的暴露方式，不含业务逻辑                        │
└──────────────────────────┬───────────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────────┐
│                     Cordis 插件内核（底座）                          │
│                                                                    │
│   ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────┐ │
│   │ 插件生命周期  │  │ 依赖注入容器 │  │  事件总线    │  │ 配置中心 │ │
│   │ 加载/卸载/回滚 │  │ Service 树 │  │  pub/sub   │  │ 组合配置 │ │
│   └─────────────┘  └─────────────┘  └─────────────┘  └─────────┘ │
│                                                                    │
│  ┌──────────────── 插件（声明式配置组合，均可替换）────────────────┐  │
│  │ core-chat(会话/聊天主循环) │ plugin-openai/deepseek(模型)      │  │
│  │ plugin-knowledge-base(RAG) │ core-storage-pg(存储)             │  │
│  └───────────────────────────────────────────────────────────────┘  │
└──────────────────────────┬───────────────────────────────────────┘
                           │ Drizzle ORM
              ┌────────────┴────────────┐
              │   PostgreSQL + pgvector  │
              └─────────────────────────┘
```

### 核心原则

1. **没有特权核心**：模型适配、RAG、存储都是插件，不在内核中特判。
2. **插件间不直接依赖**：只通过内核提供的 **Service（服务）** 与 **Event（事件）** 协作；插件间的依赖通过 `using` 声明注入。
3. **替换 = 换插件**：增强功能的方式是挂载新插件，而不是修改底座代码。

## 2. Monorepo 目录结构（规划）

```
chat/
├── apps/
│   ├── web/                    # React SPA（底座 UI）
│   └── server/                 # Fastify + Cordis 启动入口
│       └── src/
│           ├── index.ts        # 组装内核 + 加载插件 + 起 HTTP
│           └── config.ts       # 插件组合配置（哪些插件启用）
├── packages/
│   ├── shared/                 # DTO 类型、枚举、常量
│   ├── kernel/                 # 内核类型：Service/Event 接口定义、插件契约
│   └── plugin-sdk/             # 插件开发 SDK（声明 manifest、注册服务/扩展点）
├── plugins/
│   ├── core-chat/              # 会话管理与聊天主循环（底座内置插件）
│   ├── core-storage-pg/        # PostgreSQL 存储插件
│   ├── plugin-openai/          # OpenAI 兼容协议 Provider 插件
│   ├── plugin-anthropic/       # Anthropic 协议 Provider 插件
│   └── plugin-knowledge-base/  # RAG 知识库插件
├── docs/
├── data/uploads/
└── docker-compose.yml
```

> `core-*` 是随仓库发布的内置插件，但仍走与其他插件完全相同的加载机制——没有特殊权限。

## 3. 内核提供的公共服务

| Service | 职责 | 提供方 |
|---|---|---|
| `database` | 数据访问（Drizzle 实例、迁移） | core-storage-pg |
| `storage` | 文件读写（本地/S3 驱动） | 底座 |
| `config` | 插件配置读写、密钥加解密 | 底座 |
| `events` | 类型化事件总线 | Cordis |
| `http` | 注册 REST/SSE 路由的能力 | 底座（Fastify 桥接） |
| `chat.pipeline` | 聊天请求处理管线（供插件挂接拦截） | core-chat |
| `models` | 模型清单与能力查询（聚合各 provider 插件） | core-chat |
| `llm` | 流式对话调用（按 provider 分发） | 各 provider 插件注册实现 |

### 事件总线（部分关键事件）

| Event | 时机 | 订阅方示例 |
|---|---|---|
| `chat/request` | 收到聊天请求（管线入口） | knowledge-base（注入检索内容） |
| `chat/message-completed` | assistant 消息落库完成 | 用量统计插件 |
| `kb/document-ready` | 文档向量化完成 | UI 推送刷新 |
| `plugin/settings-changed` | 插件配置变更 | 失效缓存 |

## 4. 核心流程

### 4.1 流式对话时序（含插件管线）

```
前端 ──POST /chat──▶ Fastify ──▶ core-chat 管线：
                                    1. 组装 messages（历史裁剪 + 附件）
                                    2. 发布 chat/request 事件
                                       └─▶ knowledge-base 插件：
                                           检索命中 → 改写 systemPrompt（附引用源）
                                    3. models 服务解析模型 → 分发到对应 provider 插件
                                    4. provider 插件 stream() → SSE 增量回传前端
                                    5. 消息落库 → 发布 chat/message-completed
```

**中断语义**：前端 `AbortController` 断开 SSE → Fastify 通知管线 → provider 插件取消上游流 → 已生成部分落库并标记 `finishReason: aborted`。管线中所有插件监听同一 abort 信号。

### 4.2 插件加载时序（启动）

```
读取组合配置（config/plugins.ts）
  → Cordis 按依赖图拓扑排序
  → 逐个 apply 插件：
       插件声明 using（依赖哪些服务）→ 内核注入
       插件注册：services（可被他人注入）/ events 订阅 / http 路由 / UI 扩展
  → 任一步失败：回滚已加载插件（dispose），fail-fast 退出
```

### 4.3 文档入库流水线（knowledge-base 插件内部）

```
上传 → pending → ingest worker 领取 → parsing（unpdf/mammoth）
    → 语义分块 → chunks 落库 → embed（经 llm/embed 服务调用 provider 插件的 embedding）
    → ready；任一步失败 → failed（可重试，幂等：chunks 先删后插）
```

embedding 通过内核的 `llm/embed` 服务调用——**知识库插件不直接依赖任何厂商 SDK**，模型来源完全由已挂载的 provider 插件决定。

## 5. 关键设计决策

1. **内核只留四件事**：生命周期/依赖注入（Cordis）、事件总线、配置中心、HTTP 桥接。其余全部是插件。
2. **管线事件 vs 直接调用**：聊天链路采用事件管线（`chat/request` 允许插件改写请求），是因为 RAG 注入、后续的工具调用都遵循同一挂接模式；纯查询类能力（模型列表）走 Service 调用。
3. **API Key 只存服务端**：provider 插件的 key 经 `config` 服务加密落库，任何接口不外发。
4. **流式消息落库时机**：流结束后一次性落库完整内容；中断时落库已生成部分。
5. **进程内任务队列**：ingest worker 为插件内的内存队列 + 数据库状态机兜底，未来可平滑替换为队列插件。

## 6. 可观测性与配置

- pino JSON 日志：请求 ID、插件名、模型、token 用量。
- 启动时 zod 校验环境变量；插件 manifest 声明所需配置项，缺失即 fail-fast。
- `/healthz` 健康检查；`/api/plugins` 返回已加载插件清单（名称/版本/状态），便于排障。

## 7. 演进预留

- **UI 扩展点**：插件可注册设置卡片、消息操作按钮、侧栏页签（前端侧定义扩展点契约，阶段二实现）。
- **热重载**：Cordis 支持插件热卸载/重载，开发态开启，生产关闭。
- **第三方插件**：插件即 npm 包，manifest 约定 `chat-plugin` 关键字（对标 dsh 的 `dsh-plugin` topic）；阶段二再做插件市场。
