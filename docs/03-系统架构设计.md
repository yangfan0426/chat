# 03 · 系统架构设计

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        浏览器 (SPA)                           │
│   会话列表 │ 聊天窗口(流式渲染) │ 模型选择器 │ 知识库管理页     │
│        Zustand (会话/流式状态)   TanStack Query (服务端状态)    │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTP / SSE (REST + text/event-stream)
┌──────────────────────────▼──────────────────────────────────┐
│                    Fastify API Server                        │
│                                                              │
│  ┌────────────┐  ┌────────────┐  ┌──────────────────────┐   │
│  │ 会话/消息    │  │ 模型适配层  │  │ 知识库模块             │   │
│  │ Service    │  │ Provider   │  │ (解析/分块/向量/检索)    │   │
│  └─────┬──────┘  └─────┬──────┘  └──────────┬───────────┘   │
│        │               │                    │               │
│  ┌─────▼───────────────▼────────────────────▼───────────┐   │
│  │              Drizzle ORM (类型安全数据访问)              │   │
│  └───────────────────────┬───────────────────────────────┘   │
│  ┌───────────────┐       │        ┌───────────────────────┐   │
│  │ StorageDriver │       │        │ Ingest Task Queue     │   │
│  │ (本地磁盘/S3)  │       │        │ (进程内, 后台 worker)  │   │
│  └───────────────┘       │        └───────────────────────┘   │
└──────────────────────────┼───────────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              │   PostgreSQL + pgvector  │
              └─────────────────────────┘

           外部依赖：各 LLM / Embedding API（OpenAI 兼容协议）
```

### 部署形态

- `docker compose`：一个 app 容器 + 一个 postgres 容器，单机上运行。
- 上传文件挂载 volume 持久化。

## 3. 核心模块职责

| 模块 | 职责 | 关键依赖 |
|---|---|---|
| 会话模块 | 会话 CRUD、消息落库、历史分页加载 | conversations / messages 表 |
| 聊天服务 | 组装消息历史（裁剪到上下文窗口）、调用适配层、SSE 转发、落库完整消息 | Provider 适配层 |
| 模型适配层 | 按 provider 配置实例化 SDK，暴露统一 `stream()`；能力声明 | `ai` SDK 各 provider 包 |
| 知识库模块 | 文档状态机、解析、分块、embedding、检索（Top-K） | unpdf / mammoth / pgvector |
| Ingest Worker | 进程内后台任务队列，串行消费解析任务，失败重试 | 内存队列（阶段一） |
| 配置模块 | provider 的增删改查（API Key 加密落库）、模型清单管理 | providers / models 表 |

## 4. 关键流程

### 4.1 流式对话时序

```
前端                后端 Chat Service              LLM API
 │  POST /chat {conversationId, content, model}     │
 │ ───────────────────────────────────────────────> │
 │                        │ 组装 messages(系统提示+   │
 │                        │  历史裁剪+本轮+附件+RAG注入) │
 │                        │ ───── streamText() ────> │
 │ <─ SSE data: {"delta":"..."} (逐 token) ────────── │
 │                        │ <── 模型流 ────────────── │
 │ <─ SSE data: [DONE] + 完整 assistant 消息落库       │
```

**中断语义**：前端持有 `AbortController`，中断时断开 SSE 连接；后端监听 `req.raw.on('close')` 调用 SDK 的 `abort()`，将已收到的部分正文落库并标记 `finishReason: aborted`，保证历史完整。

### 4.2 文档入库流水线（RAG Ingest）

```
上传 → documents(status=pending)
   → Ingest Worker 领取 (status=parsing)
   → 存储原始文件 → 解析为纯文本
   → 语义分块 → chunks 落库 (status=parsed)
   → 调 embedding API 批量向量化 → 写向量 (status=ready)
   任一步失败 → status=failed + error 信息，前端可查看/重试
```

解析与 embedding 是 IO 密集操作，worker 内串行执行即可（个人场景吞吐足够）；每步幂等，重启后可从 failed 恢复重试。

### 4.3 RAG 问答注入（聊天时）

```
query → embed(query) → pgvector Top-K 检索(按会话关联的知识库过滤)
     → 组装 context 块(含 source 标注) → 拼入 system prompt 模板
     → 进入常规流式对话流程
```

## 5. 关键设计决策

1. **API Key 只存服务端**：前端只能通过 `GET /api/models` 拿到模型 id/名称/能力，绝不返回 key；适配层在服务端组装鉴权头。
2. **流式消息落库时机**：流结束后一次性落库完整内容（阶段一），不做逐 token 写库；中断时落库已生成部分。
3. **上下文裁剪策略**：按模型上下文窗口倒序累加历史 token（粗估：中文 1 token ≈ 0.6 字），超出则丢弃更早消息，system prompt + 最新用户消息永远保留。
4. **知识库与会话的关联**：会话级字段 `kb_ids: string[]`，可为空（纯对话）；删除知识库时校验是否有会话引用，有则提示而非强删。
5. **进程内任务队列**：不自建 Redis/BullMQ，单进程内存队列 + 数据库状态机兜底；未来需要多实例时平滑换成 BullMQ（接口一致）。

## 6. 可观测性与配置

- pino JSON 日志：请求 ID、耗时、模型、token 用量记录日志。
- 启动时用 zod 校验环境变量（`DATABASE_URL`、各 provider key 可选），配置缺失立即 fail-fast。
- 健康检查接口 `/healthz` 供 docker 探活。
